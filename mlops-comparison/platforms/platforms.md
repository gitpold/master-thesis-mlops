| **Decision** | **Option B:** Databricks |
|-------|-------|
| **Justification** | Azure ML and Databricks do not support on-premise use cases (possibly with direct connection from Azure to on-premise) but provide otherwise really feature-complete and user-friendly platforms (see latest Gartner report). MLflow would be a valid option when just looking at this comparison, but this solution would need a few additional tools to fill in the remaining components which would mean an increased integration and maintenance effort. Kubeflow has a Kubernetes dependency and even if the Kubernetes itself does not need to get managed, the effort for setting up and maintaining Kubeflow is too high. Iguazio and Weights & Biases are external services and would need to get onboarded first which is not feasible in the scope of this master thesis. Additionally Azure ML and Databricks provide more complete MLOps platforms. As both Azure ML and Databricks seem to be suitable platforms they are compared in more detail and beyond the initial scope of this evaluation: Azure ML: less cost, good integration with Azure, extensive UI, CLI & SDK, many guides & examples, nearly feature-complete regarding MLOps components. Databricks: open source focus, multi-cloud support, all important MLOps components, extensive data engineering features, support for data loading & accessibility via Unity Catalog. Databricks is chosen because of the multi-cloud support and their open source focus, as well as because the tool itself is already in use by the team and because it makes sense from a business/strategic context. |
